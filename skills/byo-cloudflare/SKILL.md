# BYO Cloudflare bridge

Windows installers provide [first-install onboarding](../../docs/ONBOARDING.md). Guide the installer through official subscription CLI authorization, Cloudflare OAuth, explicit owned account selection, one-click deployment or a secret-free prompt for their AI IDE (do not run a model CLI as the deployment agent), AC automatic-sleep consent and reversible settings (preserve locking), then real HTTPS/cost verification and valid key handoff. Never silently change an existing workstation's lock/sleep policy while testing. Completed installations bypass the wizard on daily launch and native updates; reinstall identity differs from device identity. Release/CI ownership is documented in [CI-CD](../../docs/CI-CD.md) and [RELEASE](../../docs/RELEASE.md).

For a source checkout, first read [source installation](../../docs/CROSS-PLATFORM-INSTALL.md). Run tools/install.py on Windows, then use source-install.json's Python/app/data_dir instead of the checkout. Mac installation/release status belongs to its independent maintainer and physical acceptance report; Windows work must not publish Mac. `doctor` checks prerequisites without changing login. After acceptance revoke test keys, then create a separate owner service key with `key-create --label ... --handoff`; hand its one-time message directly to the owner for a trusted IDE/server secret, never to a report or tracked file. `handoff` alone returns a key-free message. Check docs/API.md: tools are validated proposals executed by the caller; streaming and Responses are not supported.

This project has no publisher-managed endpoint. Read [the quickstart](../../docs/BYO-QUICKSTART.md) for commands and [device identity](../../docs/DEVICE-IDENTITY.md) for account changes/recovery. In an installation package these paths are relative to the installed `app` directory, alongside `BYO-Setup/` and `cloudflare/`.

1. First read [the product index](../../docs/README.md) and identify source, legacy ZIP or Windows Velopack Setup. For Setup use `current/aigo-bridge.exe setup` or `current/aigo-bridge.exe byo <command>`; only legacy ZIP uses `BYO-Setup/AIGO-Bridge-Setup.exe`. Source uses `python tools/byo_setup.py` after resolving source-install.json. `status` attaches without marking live work interrupted; reuse the existing data directory.
2. Check Node and Wrangler. Let the installer authenticate with their own Cloudflare CLI. Use `wrangler whoami` locally to select their account; do not collect/paste credentials. If more than one account is plausible and no target was specified, ask which one. Do not use a publisher account or temporary preview account. A brand-new Cloudflare account must first choose its workers.dev subdomain; if absent, use the interactive official `wrangler deploy --config <data-dir>/byo-worker/wrangler.json` after plan, then return to the setup CLI deploy for pairing. Do not answer unrelated registration/billing prompts on the user's behalf. API-only deployments cannot assume this account onboarding has already happened.
3. Run `plan --account-id <installer-account-id>`. Inspect the generated config. The persistent device ID chooses a stable unique Worker name. Existing endpoints adopt the original Worker name. Do not bypass an account/name/endpoint mismatch by erasing metadata.
4. With the user's deployment authorization, run `deploy` against that plan. It deploys only the copied template to the pinned account, sends DEVICE_KEY over stdin, and saves only DPAPI-protected device credentials. Use `pair --url` only for an already-created self-owned Worker. No plaintext secrets file is needed. Failed pairing has an encrypted pending credential for retry.
5. For Windows Setup use the actual installed console CLI, its profile binding and `byo` commands; do not expect Install.ps1 or BYO-Setup in that format. For a legacy ZIP-only install, run Install.ps1 without Launch. Read install.json for the executable and data_dir. Use `key-create --label ...` to capture a one-time key in memory (never an argv/file), `key-list` for metadata and `key-revoke --key-id ...` afterwards. Start/restart only Bridge with `--headless --data-dir ...`, test `/health`, authenticated `/api/v1/models` and a synthetic POST with that temporary key. Newly added key hashes sync on the next poll (up to about 20 seconds). Verify no original content is in logs. Record metadata only, not raw CLI diagnostics. Python is not required for the packaged flow.
6. Windows Setup uses signed `update check` / `update apply` / `update status`; profile and keys remain unchanged, and routine application updates do not redeploy the Worker. See [Windows update/adopt guide](../../docs/WINDOWS-INSTALL-UPDATE.md). For legacy ZIP/source only, pause/wait-idle and stop only the owned Bridge. Run the new installer against the same InstallRoot; it reuses install.json's data_dir and rejects accidental profile changes. Read the new install.json and use the new executable/setup CLI. Restart, then repeat deploy using the original profile. Compare device ID, URL and the same client key; never manufacture success by creating a replacement key. Custom InstallRoot/ShortcutDirectory allow isolated acceptance without replacing the owner's default shortcuts or startup entry.

Device identity is not a Claude/Codex account. Use `pause` and `wait-idle` before a user intentionally changes subscription login, then read-only CLI login status and `resume`. Never logout/re-login their active CLI on your own. This does not redeploy Cloudflare, alter URL, or rotate client API keys. Existing key holders can use the newly logged-in subscription; the owner revokes keys explicitly if that is undesired.

For model discovery and Jev integration read [the model/Decisions guide](../../docs/JEV-COMPATIBILITY.md). GET/refresh never infer; explicit probes consume usage. Preserve existing state/questions bodies and answers parsing, verify actual-model costs and incomplete receipts, and disclose uncalibrated business thresholds. Updating local code does not update the installer's Worker; new public paths require separately authorized deployment of that same device Worker. Do not silently substitute models or reuse an old HTTP success as evidence for new routes.

For a Windows-user/profile change, preserve the original authorized device DB and endpoint; DPAPI may need `repair-device-key` under the original Cloudflare owner. This rotates only the transport credential. Never promise automatic shared identity across Windows users, or unchanged workers.dev URL after moving/deleting its Cloudflare account. Detailed recovery boundaries are in the identity guide.

Do not silently fall back to a central relay. Domain purchases, billing upgrades, broad account migration, copying provider credentials, or sharing one profile across simultaneously active computers are outside normal setup.
